It started as a benchmark. It became a method.

How to run AI agents
you can trust.

Clutter-Bench began as one test: can an agent find the truth in a codebase that contradicts itself? Building a system that could pass it turned out to be the real work — and the method that came out of it is everything below.

The origin. The first question was narrow: when a codebase says one thing in its code and another in its docs, can an AI agent tell which one is true? Answering it well required more than a clever prompt. It took a whole agent system — verification habits, role contracts, blind audits, a self-improvement loop — built and hardened against hundreds of real failures. That system, and the methodology behind it, became the actual product. The benchmark is still here, and it is what the lab is named for, but the method is the thing that transfers to any codebase.

§01 — The frame

Three questions,
asked once per decision.

Most decisions are not hard. When one feels heavy, these three questions resolve most of its weight before it reaches a person.

01

Blast radius

What breaks if this is wrong? The answer’s size sets how hard you check.

02

Right target

03

Cheap probe

What this project refuses to be

Scope drifts when no one writes the edges down. Each line below names a direction this project could have taken and deliberately refused.

Nota general-purpose chatbot wrapper. It is a discipline for production agent work.
Nota place where the agent makes the final call. A human owns the irreversible decisions.
Nota finished product. It is an instrument, sharpened against real failures.
Notoptimized for cost or speed. It is optimized for output you can trust.
Nota replacement for human judgment. It gives a human better evidence to judge.
Nota knowledge graph for its own sake. Structure exists to surface contradictions.
Notimpressed by its own test scores. The benchmark is a test track, not a trophy.
§02 — The craft

The Method.

25 disciplines, stated as they were learned. Each one earned its place by preventing a specific failure that had already cost something, and they are grouped by the part of the work they govern.

Verify before you trust

00

Blast radius before verification

Every claim an agent makes about the system carries a cost if it is wrong. Rank that cost before checking it — cosmetic, degraded, corrupts downstream work, breaks the pipeline. The size of the consequence sets how hard the claim gets verified. A one-line check settles most of them in under a second; the expensive failures earn the deeper look.

01

Memory lies. Disk doesn't.

An agent's memory of a repository drifts the moment a file changes. Every factual claim about the current state earns one verifying command before it is spoken — grep, ls, wc -l. A re-read costs two hundred milliseconds. A stale claim costs a wrong decision a week later, traced back at ten times the price.

02

Discovery before verification

Verification is bounded by what someone thought to look for. The full surface comes first — git ls-files, a glob — and sampling comes second. The failure mode is confident wrongness: the sampled slice checked out while the answer sat in the slice no one opened.

03

I don't know

An agent that does not know says so, and names the one check that would resolve it. The agent admitting the gap three times an hour is the one that earns trust. A confident-sounding completion feels useful in the moment while it quietly hands over something false.

Prompting a single agent

04

Describe the risk, not the task

Pointing an agent at a location (“look in the memory folder”) yields a shallow inventory. Naming the failure to hunt (“find where this breaks once real data arrives”) forces it to reason toward real problems. The prompter becomes the director describing risk rather than a tour guide pointing at rooms.

05

The five-component prompt

A prompt precise enough that low-effort output is impossible carries five parts, each narrowing the agent: objective, severity filter, trigger condition, failure definition, and exclusions. Most prompts have one or two. The trigger condition is the strongest of them — it names the event the failure hides behind, which turns auditing into simulation.

06

Tighten the failure, never widen the scope

When results come back mixed, the instinct is to append “analyze all aspects.” That reverts to breadth and returns a blend of real problems and surface noise no one can sort. The fix runs the other direction: sharpen the failure definition until it is a net that catches everything relevant on its own.

07

Name the type, never the examples

Listing the specific failures to look for makes an agent anchor on exactly those and miss the rest. Naming the broad type — “hunt for index-file failures” — lets it surface failures no one anticipated. Prescription caps discovery at the prompter's own prior knowledge.

08

Negative identity first

The sharpest role prompts open with what the agent is not, before any positive instruction. “What You Are Not — Read This First” carves a role more reliably than a description of the job. Telling an agent the postures to refuse is what stops a synthesis role from quietly widening its own scope.

Designing the instructions

09

Attention budget is not token budget

A prompt has two budgets. The token budget is a hard wall. The attention budget is a soft gradient where quality silently decays as critical instructions land in low-attention zones. Large models read roughly uniformly; small ones have a pronounced middle-sag, so the same prompt that works on the big model degrades on the small one with no error. A fifty-token primer near the top recovers most of it.

10

Worked examples beat specifications

Handed a specification, an agent builds the blandest version that satisfies the words — the median-aesthetic version, indistinguishable from what any decent agent would produce. Two or three examples that vary along the axis that matters teach the standard prose cannot carry. More words only add text to compress past. Variation across the examples is the whole lesson; a single example just gets copied.

11

Narrative beats a bullet list

An instruction file written as the agent's own self-talk — “when I don't know, I say so” — propagates without enforcement. The same content as third-person rules requires policing every time. Identity-shaping has a lower cognitive floor than rule-application, so it holds even on weaker models. Files meant for grep stay as lists; files meant to shape behavior become story.

Running many agents

12

Subagents are blank slates

A subagent reads only the prompt it is handed. It holds none of the conversation, none of the memory, none of the project files unless they are pasted in. The prompt is the entire surface of its behavior. Ten vague prompts return ten vague answers that all get redone; one sharp prompt returns one usable result.

13

Firepower modes

Effort gets matched to the task by name. Shotgun fires eight to fifteen light parallel agents for breadth. Default runs three to five at medium depth. .50 cal is one heavy agent going deep. Stand down halts everything. The question that selects the mode is where attention buys the most, and a broad search and a subtle bug want opposite answers.

14

Coordinate through files, not chat

Let parallel agents talk to each other and coordination cost explodes with the square of their number. Route every handoff through typed files on disk instead, and the control graph collapses to near-linear. Pre-assign each agent its own output path before spawning so two writers never collide, and the filesystem layout becomes the concurrency control.

15

Verify the gate, not the artifact

“The file exists” is not “the file is correct.” A downstream stage that trusts the mere presence of an upstream output inherits every silent failure above it. Promotion waits on a verification record — a checker that confirms the artifact, captured with its hash and freshness — so a leftover file from a failed attempt can never masquerade as this attempt's work.

16

At scale, failure moves into the control plane

More agents do not remove failure; they relocate it. Two new failure modes appear and both scale: a bad task spec makes a hundred agents produce a hundred wrong answers fast, and weak checking certifies bad work with false confidence. These are more dangerous than slow execution because the error multiplies. The bottleneck stops being model capacity and becomes the quality of tasks and checks.

17

Cheap scan, expensive synthesis

Scanning and inventorying is a different job from connecting and reasoning, so they go to different models. Many cheap agents read in parallel and report facts; one expensive agent synthesizes across all of it at once. Reading sequentially loses precision by the tenth file; holding every pre-digested summary in one context at once is where the cross-cutting pattern surfaces. The synthesizer never touches raw files.

Keeping agents honest

18

Blind audits at high-stakes moments

A high-stakes write — a memory file, a ranked list of takeaways, a final artifact — gets a second reader who has never seen the conclusion, handed only the raw materials. Naming the sources it must not read is what makes the audit blind, and that is harder than naming the inputs it should use. A primed auditor is a mirror; the value is the asymmetry.

19

The cold-reader test

Parallel agents preserve structure and lose specificity, so an assembled deliverable often looks uniform where it should vary. The finished artifact goes to a reader with zero context. A cold reader judges shape rather than truth, and shape is exactly where templated, collapsed, look-alike output reveals itself.

20

Count cross-confirmations, not findings

When an artifact passes its own validation gate but a structural flaw is suspected, the cheapest credible test is six or more independent agents with overlapping-but-distinct scopes. Five converging on the same finding without being primed makes it real; one or two surfacing it makes it a hypothesis. The catch: the repetition only counts if the agents truly vary in scope, because a pipeline that cannot disconfirm itself will manufacture the same false certainty every run.

Memory and measurement

21

Retrieval beats summary-of-summaries

Summarizing summaries destroys information geometrically — a hundred thousand tokens become ten thousand, then one thousand, then noise — and still blows the budget eventually. An orchestrator does not need the full history; it needs answers to specific questions about it. Keep the record structured on disk and pull a small, query-relevant slice on demand.

22

Store the claim, point to the evidence

The durable unit of agent memory is a one-line claim with a confidence and a pointer to its evidence — a commit hash, a file, a test result — held in place of the evidence itself. The tiny claim lives in working memory; the proof is fetched only when the claim is challenged. That keeps memory cheap to carry and every conclusion traceable back to what produced it.

23

Calibration over catch-rate

Whether an agent got the answer right stops being measurable the moment real work has no answer key. Whether its stated confidence tracks its actual error rate transfers to any deployment. A calibrated agent at ninety percent beats an overconfident one at ninety-five, because buckets of “sure, unsure, treat as a lead” let a human scale judgment across the output. Flat all-certain confidence is the same warning as nothing flagged at all.

24

The self-improvement arc

The loop for fixing the tooling itself: spot the drift, write the guess at its cause down first, verify with blind agents, build the fix, cold-read it, record the lesson, ship. A guess committed before the build surfaces as a failed check instead of shipped bad code. Compute multiplies by running more of these loops, not bigger ones.

§05 — What it all rests on

Six principles.

Every discipline above traces back to a handful of commitments. These are the whole philosophy, compressed to what a fresh agent needs to make a hundred decisions without asking.

Friendship over compliance
An agent that can disagree out loud is worth more than one that always agrees.
Blast radius over ritual
The consequence of being wrong decides how hard a claim gets checked.
Disk over memory
Every claim about the current state earns one verifying command before it is spoken.
Harness over data
Improve the tool that does the work, not the test input running through it.
Compression over expansion
A tight model an agent can extrapolate from beats a verbose log it must re-read.
Say I don't know
Name the gap and the one check that would close it, instead of guessing fluently.
§06 — The method, executable

Claude Code skills.

The disciplines are not only written down. They run. These are 10 skills built for Claude Code — Anthropic’s agentic coding tool — designed and proven on it, that turn the method into one-word commands an agent fires on its own codebase.

/bootSession start
Orients a fresh session: reads the minimum canonical files, checks system health, and reports what to do next, so the agent never starts from stale memory.
/eyeCross-file drift report
Finds contradictions between files, version lag, dependency cycles, undeclared inline prompts, and hardcoded paths, then reports the top five ranked by severity.
/stress-testFind what has drifted
Cold-reads the system from several angles to surface stale docs, broken instruction chains, and quiet contradictions, then fixes them and leaves a linter behind.
/improveFix the top drift finding
Runs one self-improvement arc: take the worst finding, write the root-cause hypothesis first, verify it with blind readers, fix it, and encode the lesson. One arc, one PR.
/session-arcOne improvement cycle
Chains the whole loop end to end — detect drift, fix it, review, verify, commit — so a single command takes the system one increment better and records why.
/intakeCapture context
Drops a zero-friction structured note into durable storage, turning a passing realization or correction into state instead of letting it evaporate at session end.
/traceProcess pending notes
Scans captured notes and traces each one's implications through the system, turning a pile of raw captures into filed, addressable, acted-on knowledge.
/thinkLoad ideation context
Pulls the idea backlog, the routing rubric, and the collaboration theory into the session so it is already aligned when a new direction or brain-dump lands.
/execute-verdictImplement a confirmed brief
Takes an approved brief and implements it end to end behind verification gates, so the work ships only once a checker confirms it actually does what it claims.
/publishStatic results page
Turns raw results into a self-contained HTML page with no dependencies and no framework, openable in any browser. This very site is its output.
To be clear — these are skills for Claude Code, the coding agent that runs in your terminal and IDE. They are not chat prompts to paste into a chat window. They were designed and hardened on Claude Code and assume that runtime; the thinking behind them transfers anywhere, but the commands run there.
§07 — The benchmark this lab is named for

Clutter-Bench.

One failure mode is worth testing directly. The benchmark seeds a codebase with planted contradictions — the source code says one thing, the documentation says another — and then asks whether the agent trusts the source that runs and admits the cases where it cannot be sure.

Who pages on-call?
Code → SendGrid
Docs → PagerDuty
Where do logs ship?
Code → Datadog
Docs → Elastic
What cache runs?
Code → Memcached
Docs → Redis
The pattern
It picks the doc. The model opens the correct source file, says out loud that the two disagree, and then trusts the well-formatted documentation over the constant that actually runs — until a fifty-word reframe about what authority means flips the behavior.
Held honestly — this is an early signal. Most cells have only a single replicate so far, so the pattern above has not yet earned the word result; more runs are queued, and this page rebuilds the moment they land. Every raw run lives in the repo.
